# 6. MQTT: การส่ง message อีกรูปแบบหนึ่ง

บทที่ผ่านมาได้อธิบายการสื่อสารระหว่างโปรแกรมผ่าน ROS 2 topic แล้ว บทนี้อธิบาย
การสื่อสารอีกรูปแบบหนึ่ง คือ MQTT และเปรียบเทียบความแตกต่างระหว่างสองรูปแบบนี้

MQTT ถูกใช้อย่างแพร่หลายในอุปกรณ์จริง เช่น เทอร์โมสตัท เซนเซอร์ เครื่องจักรในโรงงาน
และแอปพลิเคชันบนมือถือ อุปกรณ์เหล่านี้เกือบทั้งหมดไม่รองรับ ROS 2 ดังนั้น
การเชื่อมต่อหุ่นยนต์เข้ากับระบบภายนอก ROS โดยทั่วไปจึงต้องใช้ MQTT

## Pub/sub ที่มี broker เป็นตัวกลาง

```
     ROS 2                              MQTT
  ┌──────────┐                     ┌──────────┐
  │  talker  │                     │ publisher│
  └────┬─────┘                     └────┬─────┘
       │ /chatter                       │ robot/<ROBOT_ID>/cmd
       │                                v
       │                          ┌──────────┐
       │  (they find each         │  BROKER  │   <-- the difference
       │   other by themselves)   └────┬─────┘
       v                                v
  ┌──────────┐                     ┌──────────┐
  │ listener │                     │subscriber│
  └──────────┘                     └──────────┘
```

หลักการเหมือนกัน คือมี publisher, subscriber และ topic ที่มีชื่อกำกับ โดยแต่ละฝ่าย
ไม่จำเป็นต้องทราบว่ามีโปรแกรมอื่นใดอยู่ในระบบบ้าง

**ความแตกต่างอยู่ที่ broker** ใน ROS 2 แต่ละ node ค้นหากันได้เอง แต่ใน MQTT
ข้อมูลทั้งหมดต้องส่งผ่าน server ตัวกลางเพียงตัวเดียว หาก broker หยุดทำงาน
การสื่อสารทั้งหมดจะหยุดตามไปด้วย

| | ROS 2 | MQTT |
|---|---|---|
| ต้องมี server ตัวกลางหรือไม่ | ไม่ต้อง | ต้อง คือ broker |
| ชื่อ topic | `/cmd_vel` | `robot/<ROBOT_ID>/cmd` |
| Message | message ที่มี type เช่น `Twist` | byte รูปแบบใดก็ได้ |
| ใช้งานผ่านอินเทอร์เน็ต | ทำได้ยาก | ทำได้โดยง่าย |
| รันบนมือถือ | ไม่ได้ | ได้ |

## การทดลองโดยไม่ใช้หุ่นยนต์

ขั้นตอนนี้เทียบเท่ากับ talker และ listener ในบทที่ 2 แต่ใช้เครื่องมือของ MQTT แทน
คอมพิวเตอร์มี broker รันอยู่แล้ว (ติดตั้งโดย `setup_pc.sh`)
หาก `mosquitto_sub` แสดงข้อความ "command not found" แสดงว่ายังไม่ได้ติดตั้ง ให้รัน
`sudo apt install mosquitto mosquitto-clients` จากนั้นดำเนินการตาม
[troubleshooting.md](troubleshooting.md#mqtt-the-gateway-dies-straight-away)
เพื่อให้อุปกรณ์อื่นเชื่อมต่อเข้ามาได้

Terminal 1 — subscribe และรอรับ message:

```bash
mosquitto_sub -t test/hello -v
```

Terminal 2 — publish:

```bash
mosquitto_pub -t test/hello -m "hi there"
```

Message จะปรากฏใน terminal 1 โดยไม่ต้องเขียนโค้ด ไม่ต้อง compile และไม่ต้อง `source`

ตัวเลือกที่ใช้:

| | ความหมาย |
|---|---|
| `-t` | **t**opic -- topic ที่ใช้รับส่ง |
| `-m` | **m**essage -- ข้อมูลที่ต้องการส่ง |

(`-v` ของ `mosquitto_sub` ใช้แสดงชื่อ topic กำกับแต่ละ message
ไม่ต้องระบุ `-h` เนื่องจาก broker อยู่บนคอมพิวเตอร์เครื่องเดียวกัน)

ขั้นต่อไปเป็นการใช้ wildcard ให้หยุด terminal 1 แล้วรัน:

```bash
mosquitto_sub -t 'test/#' -v
```

`#` หมายถึง "topic นี้และ topic ย่อยทั้งหมดที่อยู่ภายใต้" ให้ publish ไปที่
`test/hello`, `test/other`, `test/a/b/c` แล้วตรวจสอบว่าได้รับ message ทั้งหมด
ROS 2 ไม่มีความสามารถในลักษณะนี้

### เปรียบเทียบกับบทที่ 2

1. ปิด broker ด้วยคำสั่ง `sudo systemctl stop mosquitto` แล้วทดลอง publish
   ผลที่ได้เป็นอย่างไร เมื่อพิจารณาในลักษณะเดียวกันกับ `talker` และ
   `listener` มีส่วนใดที่เมื่อปิดแล้วทำให้ระบบหยุดทำงานหรือไม่
2. รัน `mosquitto_sub` บน topic ที่ไม่มีผู้ publish มีข้อความแจ้งเตือนหรือไม่
   และ `ros2 topic echo` บน topic ที่ไม่มีผู้ใช้งานให้ผลเหมือนกันหรือไม่
3. หากต้องการส่งค่าอุณหภูมิจากเซนเซอร์ที่อยู่ในอีกซีกโลก ควรเลือกระบบใด
   และหากเป็นการสื่อสารระหว่างสองโปรแกรมบนหุ่นยนต์ตัวเดียวกัน ควรเลือกระบบใด

```bash
sudo systemctl start mosquitto      # เปิด broker กลับคืนเมื่อดำเนินการเสร็จ
```

## การเชื่อมต่อกับหุ่นยนต์

หุ่นยนต์ใช้ ROS 2 ไม่ใช่ MQTT จึงต้องมี **gateway** เป็นตัวกลาง
ซึ่งเป็น node ที่ subscribe MQTT แล้ว publish ไปที่ `/cmd_vel`

```
  ┌──────────┐        ┌──────────────┐   /cmd_vel   ┌─────────────┐
  │ anything │ ─MQTT─>│ mqtt_teleop  │ ───────────> │ esp32_robot │
  │ that can │        │  (gateway)   │              │ (unchanged) │
  │ publish  │        └──────────────┘              └─────────────┘
  └──────────┘
```

**ไม่ต้อง upload firmware ใหม่** หุ่นยนต์ยังคงใช้ firmware micro-ROS จาก
บทที่ 5 และไม่ได้รับ MQTT โดยตรง สำหรับ ESP32 มีเพียงการ publish มาที่
`/cmd_vel` เท่านั้น โดยไม่มีการตรวจสอบว่าผู้ publish คือใคร

เปิด agent และหุ่นยนต์ตามขั้นตอนในบทที่ 5 แล้วตรวจสอบว่า
`ros2 node list` แสดง `/esp32_robot`

จากนั้นเปิด gateway:

```bash
ros2 launch teleop mqtt_gateway.launch.py
```

ไม่ต้องระบุ IP เนื่องจาก gateway รันอยู่บนคอมพิวเตอร์เครื่องเดียวกับ broker
และเชื่อมต่อไปที่ `localhost` (เฉพาะกรณีที่ broker อยู่บนคอมพิวเตอร์*คนละเครื่อง*
ให้เพิ่ม `host:=<that-computer's-ip>`) สำหรับหุ่นยนต์และมือถือ
ยังต้องใช้ IP จริงของคอมพิวเตอร์ โดยกำหนดไว้ใน `config.h` และในแอป

ผลลัพธ์ที่ถูกต้องคือข้อความ `robot/<ROBOT_ID>/cmd (mqtt)  ->  /cmd_vel (ros 2)` หาก
แสดง `process has died` แทน ให้ดำเนินการตาม
[troubleshooting.md](troubleshooting.md#mqtt-the-gateway-dies-straight-away)

## การขับหุ่นยนต์ด้วยคำสั่งพิมพ์

```bash
mosquitto_pub -t robot/<ROBOT_ID>/cmd -m F
mosquitto_pub -t robot/<ROBOT_ID>/cmd -m S
```

แทนที่ `<ROBOT_ID>` ด้วยชื่อที่กำหนดไว้ใน `firmware/include/config.h` หาก
กำหนดเป็น `"test"` topic จะเป็น `robot/test/cmd` gateway อ่านชื่อเดียวกันนี้
จาก `config.h` โดยอัตโนมัติ จึงไม่ต้องระบุชื่อให้ gateway หลังจาก
เปลี่ยน `ROBOT_ID` ให้รัน `colcon build` ใน `ros2_ws` เพื่อให้ gateway
ได้รับค่าใหม่
`F` เดินหน้า, `B` ถอยหลัง, `L` เลี้ยวซ้าย, `R` เลี้ยวขวา, `S` หยุด gateway จะ
แสดงคำสั่งที่ได้รับและหุ่นยนต์จะเคลื่อนที่เป็นเวลาประมาณหนึ่งวินาที
แล้วหยุดเอง พฤติกรรมนี้เป็นไปตามการออกแบบ ดูหัวข้อ "แบบฝึกหัด" ด้านล่าง

หาก gateway แสดง `'F' -> lin=+0.20` แต่หุ่นยนต์ไม่เคลื่อนที่ แสดงว่า
ปัญหาอยู่หลัง gateway ให้ตรวจสอบว่าหุ่นยนต์รัน firmware **micro-ROS** อยู่
(ไม่ใช่ motor test), agent กำลังทำงาน และ
`ros2 node list` แสดง `/esp32_robot`

gateway รองรับ JSON ด้วย สำหรับกรณีที่ต้องการกำหนดความเร็วอย่างแม่นยำ:

```bash
mosquitto_pub -t robot/<ROBOT_ID>/cmd -m '{"lin":0.1,"ang":0.5}'
```

## การตรวจสอบทั้งสามชั้นพร้อมกัน

เปิดสี่ terminal เพื่อตรวจสอบการส่งข้อมูลตลอดทั้งสาย:

```bash
mosquitto_sub -t 'robot/#' -v    # ฝั่ง MQTT
ros2 topic echo /cmd_vel                      # ฝั่ง ROS 2
ros2 node list                                # node ที่เกี่ยวข้อง
rqt_graph                                     # ภาพรวมของระบบ
```

publish คำสั่งหนึ่งครั้ง แล้วสังเกตการแปลงคำสั่งเป็น Twist และแปลงต่อเป็น PWM
บนขามอเตอร์สองขา

สิ่งที่ `rqt_graph` แสดงคือ `mqtt_teleop` publish ไปที่ `/cmd_vel`
และหุ่นยนต์ subscribe อยู่ ฝั่ง MQTT **ไม่ปรากฏ** ใน ROS 2
กราฟจะสิ้นสุดที่ gateway ในลักษณะเดียวกับที่สิ้นสุดที่ broker ใน
แผนภาพด้านบน

## แบบฝึกหัด

1. รัน `key_teleop` **และ** publish ผ่าน MQTT ไปพร้อมกัน ทั้งสองส่ง
   ไปที่ `/cmd_vel` หุ่นยนต์มีพฤติกรรมอย่างไร และพฤติกรรมนี้ถือเป็น bug หรือไม่
2. ส่ง `F` เพียงครั้งเดียวแล้วไม่ส่งคำสั่งใดอีก หุ่นยนต์เคลื่อนที่ช่วงสั้น ๆ แล้วหยุด
   เพราะเหตุใด ในระบบมี timeout อยู่ **สองตัว** ตัวหนึ่งอยู่ใน
   gateway อีกตัวอยู่ใน firmware ให้ระบุตำแหน่งของทั้งสองตัว
3. ส่งข้อมูลที่ไม่ถูกต้อง เช่น `mosquitto_pub ... -m banana` gateway ตอบสนองอย่างไร
   และ gateway ควรหยุดทำงานเมื่อได้รับ input ที่ไม่ถูกต้องหรือไม่
4. เหตุใดจึงไม่สามารถรัน `ros2 topic echo` เพื่อดู message ของ MQTT ได้

## เหตุผลที่ไม่ติดตั้ง MQTT ลงในหุ่นยนต์โดยตรง

สามารถทำได้ แต่หุ่นยนต์จะไม่เป็น ROS 2 node อีกต่อไป กล่าวคือ `ros2 bag` ไม่สามารถบันทึกข้อมูลได้
`rqt_graph` ไม่สามารถแสดงหุ่นยนต์ได้ และโปรแกรมอื่นใน ROS 2 ไม่สามารถสั่งขับหุ่นยนต์ได้

การติดตั้ง gateway ไว้บนคอมพิวเตอร์ทำให้หุ่นยนต์ยังคงอยู่ในระบบ ROS
2 และยังรองรับการเชื่อมต่อจากระบบภายนอก แนวทางนี้ คือการวางตัวแปลงโปรโตคอล
ไว้ที่ขอบของระบบ แทนการเปลี่ยนโปรโตคอลที่ระบบใช้ เป็นการตัดสินใจ
ที่พบได้บ่อยในงานวิศวกรรม
